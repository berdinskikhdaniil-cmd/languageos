# Language OS — project instructions

The durable rules of this project. Read before changing anything.

## 1. Product

Language OS is a **Telegram-first system for people learning a foreign language**.
It is not a language course and not a Duolingo competitor: the learner studies
wherever they already do — YouTube, films, podcasts, books, articles, a tutor,
conversation — and the product brings that scattered effort together as tracking,
writing, speaking, AI feedback, mistakes, vocabulary/SRS and real progress.

> **study → reproduce → feedback → fix weak points → see progress**

Before adding a feature, ask whether it strengthens that loop. If not, don't build
it without an explicit reason from the user.

## 2. Product architecture

**Telegram Bot** — the fast-interaction layer. Today it is a transport only: a
secure webhook, `/start` and `/help`, and a button that opens the Mini App. Quick
logging, start/stop, voice and reminders are *not built yet*.

**Telegram Mini App** — the main interface: home/dashboard, tracker, practice,
progress, library/vocabulary, writing, speaking, mistakes, settings. This repo is
the Mini App, and only part of it exists. Never describe planned features as if
they already work — in code, in UI copy, or in reports.

## 3. Stack

Versions come from `package.json` — check there rather than assuming.

- Next.js `16.3.1` (App Router) + React `19.2.8`, TypeScript 5
- Tailwind CSS 4, CSS-first — design tokens live in `src/app/globals.css`
- Manrope via `next/font/google`; `lucide-react` for icons
- PostgreSQL 18 (local via `docker-compose.yml`; production on Neon) + Drizzle ORM
  `0.45.2`, migrations generated by `drizzle-kit`
- Deployed on Vercel from `main` on GitHub. Local development never depends on
  either service
- `date-fns` 4 + `@date-fns/tz` for all timezone arithmetic
- Vitest 4, in two suites (§12)
- Telegram Web App bridge, loaded from `telegram.org` in the root layout
- Auth: Telegram `initData` verified server-side, then our own opaque session in an
  HttpOnly cookie — no UI framework, no AI provider, no second ORM
- Telegram Bot API: a small typed client over `fetch` in `src/lib/telegram/bot-api.ts`
  — no bot framework; add one only when a real need appears

## 4. What exists today

Working: mobile-first dashboard shell; persistent tracker on PostgreSQL; timed
sessions (start / stop / discard) and manual entries; an explicit local development
identity; the Telegram Mini App bridge; server-side `initData` validation; internal
opaque auth sessions; per-user data isolation; this-week and today analytics
computed from real rows; a minimal Telegram bot layer — a secret-verified webhook,
`/start` and `/help`, an "Open Language OS" Web App button, and explicit scripts that
configure the bot's commands, menu button and webhook; a live production deployment
on Vercel with its own Neon database, reached through @languageosbot.

The repository is public and licensed AGPL-3.0. There are two ways to use Language OS
and both must keep working: the official hosted bot, and a self-hosted copy set up from
`docs/self-hosting.md`. Nothing may assume our Vercel or Neon setup — the app must run
against any PostgreSQL and any host that can serve Node over HTTPS. Monetisation does
not exist yet; do not write copy that implies it does.

**Demo content, not functionality** — marked as such in
`src/features/dashboard/demo-analytics.ts`: the Coach recommendation and the
Errors / 1000 words trend. Never present either as a working feature. Not built at
all: Speaking AI, Writing review AI, vocabulary and SRS, the mistake engine, the
onboarding, notifications, payments. The bot logs nothing and parses no
natural language: it answers two commands and stays quiet otherwise.

## 5. Architecture invariants

Not preferences. Breaking one is a bug.

**Identity.** Feature code works from the internal `users.id`; the single entry point
is `getCurrentUser()` in `src/lib/auth/current-user.ts`. The tracker and every future
feature must never touch a Telegram user id — Telegram-specific identity stays behind
the auth boundary.

**Telegram authentication.** `initDataUnsafe` is never an authentication source.
The chain is raw `Telegram.WebApp.initData` → server-side validation → internal
auth session → HttpOnly cookie. The bot token is server-only and must never carry
a `NEXT_PUBLIC_` prefix. Never log the bot token, raw initData or a session token.

**Development auth.** The bypass is explicit: `ALLOW_DEV_AUTH="true"` *and* a
non-production `NODE_ENV`. Production must never permit it, however configured. A
failed Telegram sign-in must never fall back to the development user — separate
modes, not a fallback chain.

**Data isolation.** Every read and write is scoped to the authenticated internal user.
Never accept a client-provided user, session or language id as the source of ownership.

**Production data.** There is a real production database now. Development scripts
that delete or rewrite rows — `db:seed`, `db:reset` — go through
`assertDevelopmentDatabase()` and refuse any `DATABASE_URL` that is not this
machine's. Never weaken that guard, and never point local tooling at production
except to apply a migration on purpose.

**Database.** Never edit an already-applied migration; schema changes get a new one
that is safe on top of existing data. Prefer a PostgreSQL constraint over hopeful
application code for anything important, and never delete existing data unless asked.

**Schema changes ship additively first.** Production migrations run in the
deployment build, so for a moment the new schema is live under the old code — and a
Vercel rollback puts the old code back under the new schema for good. A migration
must therefore leave the previous deployment working. Expand, then contract:

1. an additive, backward-compatible migration (add the column, nullable or
   defaulted; add the table; add the index);
2. the code that uses it, in a later commit;
3. the destructive half — dropping or renaming — only once no deployment anyone
   might roll back to still reads it.

A rename is an add, a backfill, a code switch and a drop, spread across
iterations; never one migration. Dropping a column, dropping a table or deleting
rows needs explicit agreement from the user first — say what will be lost and wait.

**Time.** Timezone arithmetic lives in `src/lib/time.ts` and nowhere else — the
server's timezone is not the user's. Pass `now` in rather than scattering
`new Date()` boundaries through feature code; that is also what keeps rules testable.

## 6. Tracker domain rules

Activity types: `video`, `podcast`, `reading`, `conversation`, `writing`, `speaking`,
`other`. Grouping is defined once, in `src/features/tracker/domain/activity.ts`:

| Group | Activities |
| --- | --- |
| Input | video, podcast, reading |
| Speaking | conversation, speaking |
| Writing | writing |

`other` counts toward total language time but not toward those three groups.

- The active timer's source of truth is `startedAt`, never a client counter.
- A finished session's duration is recomputed server-side from its timestamps.
- One active timer per user, enforced by a partial unique index as well as in code.
- Never re-derive the activity→group mapping in a component or a query.

## 7. Design system — mandatory

`docs/design-system.md` is binding and outranks whatever a component happens to do
today. The rules most easily missed:

- Mobile-first, Telegram Mini App first; dark neutral interface
- **Green** primary accent, with dark ink on top of it
- **Manrope only.** No Inter. **No monospace anywhere in product UI**
- No neon, no glassmorphism, no generic SaaS dashboard, no developer-tool look
- No decorative percentage or status pills — write change as a sentence
- No decorative dot + label pattern
- Avoid uppercase overlines; prefer sentence case
- A filled surface takes no border
- Avoid unnecessary cardification; sections on the bare background are the default
- No decorative icon in a tile above a heading; functional icons are fine
- Spacing and typography carry the design, not decorative containers

**Never reintroduce the old blue primary accent.** Colours come from tokens in
`src/app/globals.css` — never write a hex value into a component. When building new
UI, start from the existing visual language.

## 8. Mobile and Telegram UI

Design for **360px, 390px and 430px** first. Required at all of them: no horizontal
overflow ever; tap-friendly controls; Telegram safe areas respected via the
`--safe-top` / `--safe-bottom` tokens; the bottom navigation never covering content;
bottom sheets working inside the Telegram viewport and above the navigation.
Desktop is a secondary preview — the same column, centred — not a layout target.

## 9. Code organization

```
src/app/              routes, root layout, design tokens, the auth endpoint
src/components/       auth screens, layout shell, shared ui primitives
src/db/               Drizzle schema, connection pool, env reading
src/features/<name>/  domain/ (pure rules) · data/ (queries) · actions.ts · components/
src/lib/              auth/ (identity, sessions) · telegram/ (bridge, validator, bot
                      API client, update handler) · time, format
drizzle/              generated migrations
scripts/              explicit development scripts
```

Keep the layering: domain → data access → actions → UI. Pure rules belong in `domain/`,
with no database and no clock of their own, so they stay testable without infrastructure.

Don't invent enterprise abstractions for their own sake, don't undertake large refactors
the current task doesn't need, and reuse existing helpers and invariants instead of
duplicating logic.

## 10. Next.js

This project runs a Next.js version whose APIs may differ from what you remember.
Before using or changing any Next.js-specific API, read the relevant guide in
`node_modules/next/dist/docs/` and follow `AGENTS.md` — do not rely on memory alone.
`AGENTS.md` carries a generated block maintained by `next dev`: leave it alone, and
never edit, delete or copy it here.

## 11. Working style

We work in small consecutive iterations. For each one:

1. Study the existing codebase before writing anything.
2. Understand the current architecture.
3. Implement only the scope of the current prompt.
4. Do not start the next product iteration on your own.
5. Leave the project in a working state.
6. Run the checks yourself.
7. Fix regressions you find.
8. Never leave an obviously broken runtime.

Don't produce a roadmap instead of doing the work, and don't implement neighbouring
features "while you are in there".

If a prompt conflicts with the current architecture or with this file, stop and explain
the conflict plainly rather than quietly restructuring the system. A direct new
instruction from the user takes priority over an older project convention — say so,
then follow it.

## 12. Verification

After meaningful code changes:

```bash
npm test           # unit suite — no database, no network
npm run test:db    # integration suite — needs `npm run db:up`
npm run lint
npm run typecheck
npm run build      # does not require a database
```

`npm run test:db` is required whenever persistence, auth or data isolation is touched.
After pushing a schema change, read the deployment: the build log must show the
migration step succeeding, and the app must still answer afterwards.
For UI changes also verify at runtime in a browser when the environment allows, at the
widths in §8.

Report outcomes honestly: **never claim a real Telegram end-to-end check** unless the
app was launched from a real Telegram client. A simulated bridge is a simulated bridge —
say which you used.

## 13. Git

- Check `git status` before starting.
- Never mix unexpected user changes into your own work — stop and ask.
- No destructive resets. Never squash earlier iterations unless asked.
- Commit only when the prompt asks for it.
- Never commit secrets. `.env` is ignored; `.env.example` is the template.
- GitHub `berdinskikhdaniil-cmd/languageos` is the canonical repository, and it is
  public under AGPL-3.0. Anything committed is published; the private product handoff
  is ignored and stays off it. `README.md`, `docs/self-hosting.md`, `CONTRIBUTING.md`
  and `SECURITY.md` are read by strangers — keep them accurate, and never describe a
  planned feature there as if it worked.
- Pushing `main` deploys production, through Vercel's Git integration with that
  repository. A direct `vercel deploy --prod` is no longer the normal way to ship —
  reach for it only to recover when the integration itself is broken.
- Production migrations are part of that build: `vercel.json` runs
  `npm run db:migrate:deploy` before `next build`, so a migration that fails fails
  the build and the previous deployment keeps serving. Nothing is applied by hand,
  and preview deployments never touch the production database.
- Never run `vercel env pull` here without an explicit destination: it overwrites
  local development env with production credentials.

## 14. Known limitations

- Production is one Vercel project and one Neon database, with no staging
  environment between them: `main` deploys straight to production, migrations
  included. Two production builds racing would both try to migrate; one would fail
  and take its deployment with it.
- Every Mini App launch mints a new auth session row; nothing reuses or prunes them
  yet (see the session-lifecycle limitation below).
- The bot is a door, not a feature surface: no logging by message, no voice, no
  reminders, and `/start` payloads are parsed but unused.
- A new user's first language is hardcoded to English — a temporary product decision
  until onboarding exists, not an architectural rule.
- Timezone comes from `DEFAULT_TIMEZONE`; users cannot set their own yet.
- Session revocation and expired-row cleanup exist in `src/lib/auth/session.ts` but
  are wired to no UI and no schedule; there is no session rotation and no logout.
- The bottom sheet has focus-on-open, Escape and scroll lock, but no full focus trap.
- A session crossing midnight counts entirely toward the day it started on.
